# Seshlehem Open — Technical Implementation Plan

## 1. Technical decision
Build a **mobile-first React single-page application** with a very small serverless HTTP API and SQL database.

### Recommended production stack
| Layer | Technology |
|---|---|
| Frontend | React + TypeScript + Vite |
| Styling | Tailwind CSS |
| Routing | React Router |
| Server state | TanStack Query |
| Forms | React Hook Form + Zod where useful |
| Domain logic | Plain TypeScript pure functions |
| API | Cloudflare Worker |
| Database | Cloudflare D1 |
| Hosting | Cloudflare Worker Static Assets |
| Unit/component tests | Vitest + React Testing Library |
| E2E smoke tests | Playwright |
| Source/CI | GitHub |

This plan supersedes older stack references in `GOLF_TRIP_APP_REQUIREMENTS.md`.

## 2. Why this architecture
This is a seven-person friends app. Optimise for:
1. reliable score entry;
2. correct Stableford calculations;
3. fast mobile UX;
4. free/near-zero operating cost;
5. simple code Codex can maintain next year.

Avoid SSR, microservices, GraphQL, Redux, websocket infrastructure, containers and complex identity.

React/Vite is preferable to Next.js because there is no SSR/SEO requirement and it keeps the frontend portable to almost any static host.

## 3. High-level architecture

```text
Phone browser
    |
    v
React / Vite SPA
    |
    | HTTPS JSON /api/*
    v
Cloudflare Worker
    |
    v
Cloudflare D1
```

Cloudflare hosts the SPA and API under one deployment. D1 stores the shared trip/course/player/score data.

## 4. Hosting options
### Default: Cloudflare Worker + D1
Preferred because frontend, API and database can live in one small deployment and free-tier capacity is far above this app's usage.

Expected initial primary scores are only:
`7 players × 18 holes × 2 rounds = 252 score rows`.

### Fallback: Vercel + Supabase
Good alternative if Cloudflare D1/Workers create a concrete development blocker. Keep the same React UI and API contracts; map persistence to Supabase/Postgres.

### Optional: Azure
If Visual Studio subscription credits are useful, map to:
- Azure Static Web Apps
- Azure Functions
- a small Azure database/storage option

Do not make Azure the default solely because credits exist; it adds configuration without adding value for seven users.

## 5. Portability rule
Keep Cloudflare-specific code behind the API/persistence boundary. React components must not directly depend on D1 APIs.

Use frontend contracts similar to:

```ts
interface GolfApi {
  getActiveTrip(): Promise<TripOverview>;
  getRound(roundId: string): Promise<RoundDetail>;
  saveScore(input: SaveScoreInput): Promise<SavedScore>;
  getRoundLeaderboard(roundId: string): Promise<RoundLeaderboard>;
  getOverallLeaderboard(tripId: string): Promise<OverallLeaderboard>;
  getTripStats(tripId: string): Promise<TripStats>;
}
```

## 7. Database design
Use D1/SQLite migrations. Prefer text UUIDs generated by the API or suitable IDs generated consistently.

### trips
- id PK
- name
- start_date nullable
- end_date nullable
- active boolean/default
- created_at

### players
- id PK
- display_name
- short_name nullable
- is_admin boolean
- active boolean

### trip_players
- id PK
- trip_id FK
- player_id FK
- default_playing_handicap integer
- unique(trip_id, player_id)

### courses
- id PK
- name
- location nullable

### tees
- id PK
- course_id FK
- name
- total_yards nullable
- par nullable
- course_rating nullable
- slope_rating nullable

### holes
- id PK
- tee_id FK
- hole_number integer
- par integer
- stroke_index integer
- yards integer nullable
- unique(tee_id, hole_number)

### rounds
- id PK
- trip_id FK
- course_id FK
- tee_id FK
- round_number integer
- name
- round_date nullable
- status: upcoming/in_progress/complete
- competition_type default stableford

### round_players
- id PK
- round_id FK
- trip_player_id FK
- playing_handicap integer
- unique(round_id, trip_player_id)

### groups
- id PK
- round_id FK
- name
- tee_time nullable

### group_players
- id PK
- group_id FK
- round_player_id FK
- unique(group_id, round_player_id)

### scores
- id PK
- round_player_id FK
- hole_number integer
- gross_score integer nullable
- picked_up boolean default false
- created_at
- updated_at
- unique(round_player_id, hole_number)

Do not store Stableford totals as mutable source data. Derive them from holes + score + playing handicap.

## 8. Domain logic
Keep golf calculations pure and independent of React/Worker/D1.

Required functions:

```ts
getHandicapStrokes(playingHandicap: number, strokeIndex: number): number
getNetScore(grossScore: number, strokes: number): number
getStablefordPoints(par: number, netScore: number): number
isBirdie(grossScore: number, par: number): boolean
isTwo(grossScore: number): boolean
```

Stableford:

```ts
Math.max(0, 2 + par - netScore)
```

Positive handicap allocation:

```ts
const base = Math.floor(handicap / 18);
const remainder = handicap % 18;
return base + (strokeIndex <= remainder ? 1 : 0);
```

Treat Pick Up/NR as zero Stableford and excluded from birdie/2 calculations.

## 9. API design
Keep it boring REST/JSON. Example routes:

### Public/read
- `GET /api/trips/active`
- `GET /api/trips/:tripId`
- `GET /api/trips/:tripId/players`
- `GET /api/trips/:tripId/leaderboard`
- `GET /api/trips/:tripId/stats`
- `GET /api/rounds/:roundId`
- `GET /api/rounds/:roundId/groups`
- `GET /api/rounds/:roundId/leaderboard`
- `GET /api/rounds/:roundId/scorecard/:roundPlayerId`

### Scoring
- `PUT /api/rounds/:roundId/players/:roundPlayerId/scores/:holeNumber`

Use PUT/upsert semantics so editing a hole does not double count.

### Admin
Use straightforward CRUD under `/api/admin/...` for trips, players, courses, tees, rounds and groups. No need to create a generic admin framework.

## 10. Validation
Validate on the API even though security requirements are low.

At minimum:
- IDs exist and relate to the target trip/round
- hole 1–18
- gross score sensible range or pickup
- playing handicap integer in a sensible range
- one score per round player/hole

Client validation improves UX but server validation owns persistence integrity.

## 11. Identity/admin model
On first visit select a player and store `selectedPlayerId` in localStorage.

Normal UI allows edits only for that player. Admin users get an Admin entry point and score override UI.

Do **not** treat this as secure authorization; the app is deliberately low-security. Avoid pretending otherwise in code/comments.

## 12. Client state
- TanStack Query for server data/cache/refetch
- local component state for score controls
- localStorage only for selected player and harmless UI preferences
- no Redux/global state framework

After a successful score save:
- update/invalidate current scorecard
- invalidate round leaderboard
- invalidate trip overall leaderboard and stats

## 13. Live updates
No websocket/realtime infrastructure for MVP.

When a leaderboard/stats screen is visible:
- refetch approximately every 10 seconds
- refetch on window focus
- immediately refresh related queries after local score save

This is more than adequate for seven golfers.

## 14. Mobile UX requirements
The scoring flow gets highest UX priority.

### Score entry screen
Header/card:
- Round / course
- Hole N
- Par / SI / yardage
- strokes received

Main control:
- large score buttons or +/- control
- obvious selected score
- instant Stableford point preview
- result badge (birdie/par/etc.)
- Pick Up option

Navigation:
- Previous Hole
- Save & Next (or autosave plus Next if implementation is very clear)

Prefer one-handed usage and >=44px touch targets.

### Bottom navigation
Home / Leaderboard / Scorecard / Stats / More.

## 15. Leaderboard calculation
Return normalized rows rather than making every component recalculate independently.

Round row should include:
- player id/name
- holes completed
- gross total where meaningful
- Stableford total
- position/tied position

Overall row:
- player
- per-round points
- combined total
- position/tied position

Countback is optional after MVP.

## 16. Statistics
Derive from saved gross scores:
- birdie: gross == par - 1
- 2: gross == 2 on any hole

Do not confuse gross birdies with net Stableford birdies.

## 17. Moray seed data
Add reproducible seed data for Moray Old/New course hole definitions and the tees chosen/available for the trip.

Requirements:
- migration creates schema
- seed script inserts courses/tees/18 holes each
- data can be re-run safely or reset clearly for development
- generic business logic never assumes those course IDs

Player names/handicaps may initially be configured through admin unless explicitly provided later.

## 18. Error handling
Score saving failure must be prominent:
`Couldn't save your score. Check your connection and try again.`

Keep the user's selected value on screen so retry is easy. Never optimistically show a persisted state as final if the write failed.

Other friendly states:
- no active trip
- no current round
- round not started
- no scores yet

## 19. Testing strategy
### Unit tests — mandatory
Test Stableford/handicap allocation thoroughly, especially 0, 6, 18, 20 and 36 handicaps and score edits.

### Component tests
Focus on:
- player selection
- scoring control
- leaderboard loading/error/empty states

### API tests
Test score upsert + validation and key leaderboard aggregation where practical.

### Playwright
Keep to critical mobile smoke paths:
1. select player
2. open round
3. enter score
4. verify scorecard/leaderboard reflects it
5. edit score and verify totals change

Run with a mobile-sized viewport.

## 20. CI and deployment
At minimum a GitHub workflow/CI command should validate:
- install
- lint
- typecheck
- unit tests
- production build

Production deployment can be connected to Cloudflare after the application foundation works. Avoid committing API tokens/secrets.

Expected environment/config items:
- Cloudflare account/project binding configuration
- D1 database binding
- no client-side secret credentials

## 22. Definition of done
The MVP is done when seven friends can open one HTTPS URL on their phones, select their name, enter/edit their own hole scores, see correct Stableford points and live-ish shared round/overall leaderboards, and view birdie/2s standings.

The same code/database model must allow a new future Seshlehem Open trip without changing generic business logic.
